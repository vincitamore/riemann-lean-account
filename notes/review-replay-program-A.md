Totals: 2 unsound, 1 gap, 3 fragile, 6 note.

## Verdict

False acceptance is possible, for environments the kernel cannot produce. Inductive and quotient constants are counted as replayed but never compared with what the kernel builds from them (findings 1 to 3). The strongest case: a loaded inductive type lists as a constructor a name that the loaded environment binds to an unsafe definition. The kernel then builds a safe constructor under that name, and a theorem that uses it is accepted, although against the loaded environment the kernel rejects it (finding 2, case b). Weaker cases: a loaded inductive constant whose name is not in the block sent for it, or a quotient constant under any name, is counted as replayed and never checked or compared. Lean's own replay at v4.33.1 has the same holes, except the two of finding 3, where it fails and this program does not. Every case needs constants that no kernel call produced, that is, code that writes to the environment directly; the archive runs code at elaboration (`scan.txt`: 4 files with `elab`, 5 with `run_cmd`), which this review did not read.

What the holes cannot do. Every constant of the replayed environment is kernel-checked or kernel-generated (finding 4), so a theorem accepted there is a kernel-accepted consequence of the axioms in that environment. A constant that was never checked is absent from it, so nothing checked can use it, except through the name confusion of finding 2. In the published run the five theorems of `Main` are theorems in the loaded environment (kind `T` in `cut-in.txt.xz` and `cut-out.txt.xz`), each was checked as a theorem, no failure was recorded, and the statement `RiemannHypothesis` is a Mathlib definition, so by the import structure its cone lies in Mathlib, its dependencies and Lean's library. I found nothing that makes the published verdict on the five theorems wrong. Beyond the trust that every kernel check carries (finding 10), it could be wrong only if the loaded oleans held malformed inductive types inside that cone, which the program would not notice. The findings change what "2,695,292 declarations replayed, none rejected" may be said to mean (finding 9).

## Paths through `emit`, by kind

- `defnInfo`, `thmInfo`, `opaqueInfo`, `axiomInfo` (safe): the kernel checks the loaded declaration in a task against the snapshot (`addDeclCore`); the main thread adds the same declaration unchecked, so the added constant is the loaded one. Nothing is trusted beyond the kernel.
- Other versions of a repeated name (lines 160-169): theorems, definitions and opaque constants are checked against the same snapshot as the kept version and not added; axioms are ignored; other kinds cannot occur (finding 7). The kept version is the last in module order (line 231).
- `inductInfo` (lines 183-195): the first member reached sends the block, built from the loaded member names, types, constructor names and constructor types, with that member's level parameters and parameter count and `isUnsafe := false`, through `addDeclCore` on the main thread. The loaded `InductiveVal` is trusted: it is never compared (findings 2, 3).
- `ctorInfo`, `recInfo` (lines 196-197, 267-274): not sent; compared at the end with the kernel's constant by the derived `BEq`.
- `quotInfo` (lines 198-203): the first sends `.quotDecl` (with `Eq` ordered before it, line 91); none is compared (finding 1).
- Unsafe or partial (line 230): never added. A safe declaration that uses one is rejected with `unknownConstant`; were it present, the kernel would reject it for using an unsafe or partial constant (`type_checker.cpp:110-117`). So none can support an accepted declaration, except through finding 2, case b.

## Findings

1. **Quotient constants are counted and never compared (unsound).**
   Lines: 91, 198-203; nothing after line 264 looks at them.
   What could go wrong: every `quotInfo` in `order` increments `nQuot`; the first sends `.quotDecl`, after which the kernel's `add_quot` returns at once (`quot.cpp:48-49`). No `quotInfo` is compared with the constant the kernel made, and one under any other name is neither added nor checked nor reported.
   Scenario: code run at elaboration inserts `ConstantInfo.quotInfo { name := X, levelParams := [], type := P, kind := .type }` for a proposition `P`. The replay counts it (the current version prints `quotient-constants 5`; the published version had no such line), adds nothing, reports `failed 0` and exits 0. In the loaded environment `#check (X : P)` succeeds and `#print axioms X` reports no axioms, since `CollectAxioms` treats a quotient constant as a leaf (`CollectAxioms.lean:63`). Lean's replay does the same (`Replay.lean:129-133`). Bound: `X` is absent from the replayed environment, so any checked declaration that mentions it fails with `unknownConstant`; `X` can only be a leaf. In the published run no archive declaration has kind `Q` in the cut lists, and `replayed` minus the sum of the published kinds is 4.
   Fix: after the final `drain`, for every `quotInfo` name `n` in `order`, require `n` to be `Quot`, `Quot.mk`, `Quot.lift` or `Quot.ind`, and `kenv.find? n` to be a `quotInfo` with equal name, level parameters, type and kind; otherwise `fail`. `QuotVal` and `QuotKind` derive no `BEq` at this tag (`Declaration.lean:416, 420`); `deriving instance BEq for QuotKind, QuotVal` in the program supplies it.

2. **Inductive types are never compared with the kernel's, and some loaded constants are never examined (unsound).**
   Lines: 183-195, 196, 267-270.
   What could go wrong: (a) the block is assembled from `info.all` (line 187) with no check that `n` belongs to it; if it does not, `n` itself is never added, checked or compared. (b) Constructor names are resolved to whatever `all[c]` holds (line 191 takes `cc.name` and `cc.type` of a constant of any kind), and only names whose loaded constant is a `ctorInfo` are compared (lines 196, 267). (c) The kernel's `InductiveVal` for each member (indices, `all`, `ctors`, nesting, recursiveness, reflexivity, safety, and the level parameters and parameter count, which line 195 takes from `n` for every member) is never compared with the loaded one; `InductiveVal` derives no `BEq` at this tag (`Declaration.lean:302`). (d) In the other direction, nothing checks that each constant the kernel generates (constructors, recursors, nested auxiliaries) exists in the loaded environment; a declaration that uses a generated name the loaded environment lacks is checked against the kernel's constant (line 256 lets the missing name pass). (e) The name a constant is filed under (`constNames`, line 224) is never compared with its own `name` (line 225), under which the kernel adds it; a constant filed under one name but carrying the name of a skipped constant gives that name a safe binding, with the same effect as (b).
   Scenario for (a): insert `inductInfo { name := X, type := P, all := [Y], ctors := [], numParams := 0, numIndices := 0, .. }`, with `Y` declared normally as `unsafe inductive Y : Prop`. `Y` and `Y.rec` are skipped (line 230) but stay in `all`; `X` is safe, so it is in `order`; emitting `X` sends the block `[Y]` as safe, which the kernel accepts as an empty proposition; `X` is counted once under `inductive-types`, `sum-of-the-kinds` balances because `Y` is not in `order`, and the run reports `failed 0`. In the loaded environment `X : P` is an inductive type whose type is a proposition, which the kernel cannot produce. Lean's replay does the same (`Replay.lean:102-120`).
   Scenario for (b), where a checked declaration is affected: the loaded `inductInfo Foo { type := Prop, ctors := [T], all := [Foo], .. }` with `T` an unsafe definition `T : Foo` (skipped) instead of a constructor, and a safe theorem `S : Foo := T`. The kernel builds `Foo` with a safe constructor `T : Foo`; `T` is never compared, because its loaded kind is not `ctorInfo`; `S` is accepted. Against the loaded environment the kernel rejects `S` ("invalid declaration, it uses unsafe declaration 'T'", `type_checker.cpp:110-113`). Lean's replay builds the same block from `newConstants[T]!`, which holds unsafe constants too.
   Bound: the replayed environment is still made only of kernel-checked and kernel-generated constants, so whatever is accepted is a kernel-accepted consequence of its axioms; what is lost is the identity of the replayed environment with the loaded one that `check.sh` reads. For the five theorems this matters only if an inductive type in the cone of their statements is malformed in one of these ways.
   Fix: (i) at line 225 require `ci.name == n`; (ii) in the block assembly, fail unless `n` is in `info.all` and every name in every member's `ctors` is a `ctorInfo` in `all` whose `induct` is that member; (iii) after the final `drain`, for every `n` in `order`, require `kenv.find? n` to exist, to be of the same kind, and to equal the loaded constant field by field (`deriving instance BEq for InductiveVal, QuotKind, QuotVal, ConstantInfo` makes this one comparison; for definitions, theorems, opaque constants and axioms it holds by construction); (iv) for every constant of the final `kenv`, require its name in `order`. Make every mismatch a failure. This one reconciliation pass also closes findings 1 and 3.

3. **Two cases where Lean's replay fails and this program accepts (gap).**
   Lines: 185, 190-191.
   What could go wrong: (i) `filterMap` drops a listed constructor that no module declares, and the kernel builds a type with fewer constructors. Lean's replay looks the constructor up with `newConstants[n]!` (`Replay.lean:109-111`); the lookup panics and yields the default constant, an axiom named `[anonymous]` whose type is the constant `_inhabitedExprDummy` (`Expr.lean:516-518`), and the kernel rejects that block. (ii) Line 185 returns early whenever the name is already bound, which is meant for the other members of a block but also skips an inductive whose name was bound by another block's generated constant. Lean's replay decides by its `pending` set (`Replay.lean:79, 106-108`), sends the block, and the kernel fails with `alreadyDeclared`.
   Scenario: (i) the loaded `Foo` lists `[a, b]`, no module declares `Foo.b` or `Foo.rec`, and a theorem `∀ x : Foo, x = Foo.a` is proved with `Foo.rec`; the replay builds a one-constructor `Foo` whose generated `Foo.rec` has one minor premise, and accepts the theorem, which the kernel rejects against the loaded environment (`Foo.rec` unknown). (ii) The loaded environment holds an `inductInfo` named `Bar.rec` and lacks the recursor `Bar.rec`; once `Bar`'s block is added, `Bar.rec` is skipped at line 185 and never examined.
   Fix: fail when a listed constructor is missing; record the names of every block sent and return early only for those; the reconciliation pass of finding 2 then reports anything left.

4. **The parallel scheme (note: sound).**
   Lines: 95-104, 131-147, 160-169, 264.
   Why: (i) the snapshot cannot change under the task: `Task.spawn` marks its closure and everything reachable from it as shared between threads (`object.cpp:1169-1170`), and such objects are never treated as exclusive (`lean.h:704-710`), so the update at line 144 copies instead of writing in place. (ii) The task checks and the main thread adds the same `d` against the same `snap`. `addDeclWithoutChecking` does not test the name (`environment.cpp:297-301`), but whenever it overwrites, the paired check fails with `alreadyDeclared` (`environment.cpp:102-105, 128`); the kernel tests every name it generates (`inductive.cpp:259-260, 371, 514, 814`; `quot.cpp:53-56`). So in a run with no failure each binding of the final environment was written once and is kernel-checked or kernel-generated. (iii) Every task enters `pending` as it is created (lines 143, 168); `drain` copies `pending` before clearing it and waits on every copied task (lines 131-137); it runs at the window (line 147) and unconditionally after the traversal (line 264); the self-test waits on its own two tasks. (iv) Every exception the kernel raises becomes `.error` (`kernel_exception.h:161-217`) and line 137 records it; the program catches no `IO` error, so one ends `main` with a nonzero code, and a crash or abort ends the process. The other versions of a repeated name are checked against the same snapshot as the kept version. Each check sees every declaration emitted before it, a superset of its dependencies, which is harmless.
   What it does not give: the content of inductive and quotient constants in the snapshot is the kernel's, not the loaded one (findings 1 to 3).

5. **Dependency order: a wrong order gives only false failures (note: confirmed).**
   Lines: 73-93, 232-263.
   Why: bindings are written once (finding 4), so a declaration checked before one of its dependencies finds the name unbound. `infer_constant` calls `environment::get` for every constant occurrence (`type_checker.cpp:101-102`; `environment.cpp:78-85` throws `unknown_constant_exception`); `check` visits every subterm of the type and the value with `infer_only` false (`type_checker.cpp:325-357`); a projection looks its structure up the same way (`type_checker.cpp:259`). A declaration can never see a different binding. Cycles are the same case. A dependency that no module declares (line 256) is skipped by the traversal; the declaration that mentions it is still checked and rejected, unless the kernel itself generates that name, in which case the kernel's constant is used (finding 2, case d).

6. **`usedConstsImpl` and addresses (note: sound).**
   Lines: 37-64.
   Why: Lean frees objects by reference counting and never moves them. Every node visited in one call is a subterm of `e`, which the caller holds through `ci` in `all` for the whole call, and terms read from `.olean` files live in compacted regions that are not freed while the environment lives; so no visited address can be freed and reused during a call, and `visited` does not outlive it. Reuse of a node's memory needs the node to be exclusive, which a shared subterm is not. A missed constant would only shift the order, a false failure (finding 5).

7. **Safety classification and repeated names rely on `finalizeImport` (fragile).**
   Lines: 158-169, 226-231.
   What could go wrong: safety is decided on the first version of a name (line 230), the kept version is the last (line 231), and repeated inductive types, constructors and recursors would be ignored (line 165). If the versions disagreed, a safe kept version would never be emitted (status 2 at line 240) and would be listed in `replay-skipped.txt` as unsafe or partial, and an unsafe one would be checked under unsafe rules.
   Why it does not happen today: `importModules` (line 213) builds the environment through `finalizeImport`, which throws on a repeated name unless `subsumesInfo` holds one way (`Environment.lean:2268-2300, 2334-2343`): theorem and theorem with equal type, level parameters and `all`; theorem and safe axiom; axiom and axiom with equal safety and a propositional type. So the other versions are theorems or axioms of the same type and the same safety. Consequences: the summary's "of which with a different type" (lines 169, 291) is 0 for every environment the program can load and carries no information. For a theorem followed by an axiom, Lean keeps the theorem, while this program keeps the axiom and lists it in `replay-axioms.txt`; this is conservative, and the published list has only the seven standard axioms. The comment at line 158 ("private declarations") should say repeated theorems; private names carry their module. In the run `dup` equals `nAlt` (40,595), so every other version was a theorem, and all were checked, which Lean's replay does not do.
   Fix: classify by the kept version and fail if two versions differ in kind, type, level parameters or safety; keep a theorem over an axiom as `finalizeImport` does.

8. **The self-test (fragile).**
   Lines: 276-282.
   What it establishes: the compiled `spawnCheck` reaches the kernel and is not optimized away; it returns `none` for a correct theorem and `some` for a type mismatch; `True`, `False` and `True.intro` are in the final environment with their expected types.
   What it does not: that `drain` records a `some` (the self-test reads the task directly, so swapping the two arms at lines 136-137 would pass it); that a failure of `checkedNow` and the constructor and recursor comparisons can fire; that the kernel rejects a reference to an absent constant, which is what protects against the 5,840 skipped constants; that every loaded declaration was emitted; that what was added is what was checked. `rejects-false` accepts any error, so it would also pass if `False` were missing.
   Fix: before the main run, send a small fixture through the same `emit`, `drain` and comparison code on a scratch state: a theorem with a wrong proof, a theorem that uses a skipped unsafe constant, a repeated name, a constructor with one field changed, and the spoofs of findings 1 and 2; require exactly those names in `failures`, with the expected exception kinds.

9. **Exit code and summary (fragile).**
   Lines: 285-300.
   What could go wrong: exit 0 needs only an empty `failures` and the self-test. Not part of it: the unsafe and partial constants (by design, and listed); findings 1 to 3; `counted == order.size`, printed only (line 289); panics, which print to standard error and continue (lines 222-225, 245, 247, 250). Each panic I traced either cannot occur or ends in a recorded failure: a `constants` array shorter than `constNames` yields the default axiom of finding 3, whose type the kernel rejects as an unknown constant. Line 286 prints as `replayed` the number of names in `order`. The published 2,695,292 is: 2,644,463 checked in tasks (theorems, definitions, opaque constants, axioms); 15,769 inductive types rebuilt by the kernel from their loaded types and constructor types, their `InductiveVal` not compared; 19,159 constructors and 15,897 recursors compared with the kernel's; 4 quotient constants made by the kernel and not compared. The 40,595 other versions of theorems were checked and are not in that count. `names-declared-more-than-once` (line 291) counts extra declarations; it equals a count of names only if no name is declared three times.
   Fix: make the reconciliation of finding 2, `counted == order.size` and the absence of panics (run with `LEAN_ABORT_ON_PANIC=1`, or replace the `!` accesses) conditions of exit 0, and let the paper quote the decomposition rather than one number.

    - Checked by Lean's replay and not here: the two cases of finding 3. Nothing else.
    - Checked here and not by Lean's replay: every other version of a repeated theorem (with `--fresh`, Lean replays `env.constants.map₁`, one version per name, `LeanChecker.lean:36-38`, and `Replay.lean:84-97` skips a theorem identical to one already present); a missing block member is a recorded failure (Lean panics on `newConstants[n]!`); the run continues after a failure and reports all of them (Lean throws at the first).
